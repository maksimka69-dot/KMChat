# Кибершкола: Переводчик-переговорная

Одностраничное веб-приложение для видеозвонков с **автоматическим переводом речи в реальном времени**. Два человека говорят каждый на своём языке — приложение распознаёт речь, переводит её и показывает собеседнику перевод текстом почти без задержки, поверх обычного видеозвонка.

Это первая, минимальная версия (MVP) — звонок 1 на 1. Она сделана, чтобы обкатать саму концепцию и связку технологий, прежде чем усложнять архитектуру под настоящий сценарий использования — занятие с ведущим и группой до 15 человек (см. раздел [«Куда это движется»](#куда-это-движется-дальнейшее-развитие)).

---

## Идея проекта

Кибершкола — это международный/многоязычный формат обучения: ведущий и слушатели могут говорить на разных языках. Печатать и вручную переводить сообщения в чате во время живого занятия неудобно и разрушает ощущение живого разговора. Задача приложения — снять языковой барьер прямо во время звонка:

1. Человек говорит в микрофон на своём языке.
2. Речь распознаётся и превращается в текст (Speech-to-Text).
3. Текст переводится на язык собеседника (Machine Translation).
4. Перевод мгновенно показывается собеседнику текстом на экране — рядом с видео.

Видео и звук при этом идут напрямую между участниками (P2P), а переводится только текст — это делает решение быстрым и не требует серверной инфраструктуры для видео.

## Как это работает (архитектура MVP)

Всё приложение — это **один HTML-файл** (`translator.html`) без сборки, бэкенда и зависимостей, кроме пары внешних скриптов/API, подключаемых прямо в браузере.

```
Говорящий                                              Слушающий
   │                                                        │
   │ 1. Микрофон → AudioWorklet → PCM16 mono 16kHz           │
   ▼                                                        │
Deepgram (WebSocket, Nova-3 Multilingual)                    │
   │ 2. Распознанный текст (interim + final)                 │
   ▼                                                        │
MyMemory Translation API (HTTP)                              │
   │ 3. Перевод текста                                       │
   ▼                                                        │
PeerJS DataChannel  ───────────────────────────────────────► │
                                                          4. Показ перевода в UI
   │                                                        │
   └──────────────── видео/аудио звонка (WebRTC, напрямую) ──┘
```

### Ключевые технологии

| Слой | Технология | Зачем |
|---|---|---|
| Видеозвонок | [PeerJS](https://peerjs.com/) (обёртка над WebRTC) | P2P-видео/аудио между двумя браузерами, используя публичный сигнальный сервер PeerJS Cloud для установления соединения |
| Комнаты | 4-значный числовой ID | Простой способ подключиться к собеседнику без регистрации/бэкенда |
| Распознавание речи (STT) | [Deepgram](https://deepgram.com/), модель **Nova-3 Multilingual** (`model=nova-3&language=multi`) | Стриминговое распознавание речи в реальном времени, поддержка русского и 35+ языков в одном подключении, включая переключение языка «на лету» |
| Перевод текста | [MyMemory Translation API](https://mymemory.translated.net/) | Бесплатный REST-перевод текста между языками |
| Хранение настроек | `localStorage` | Запоминает выбранный микрофон между сессиями |

### Почему именно так

- **Один HTML-файл** — осознанный выбор для MVP: можно открыть где угодно, без сборки, легко тестировать и передавать.
- **Deepgram, а не браузерный Web Speech API** — Web Speech API у большинства браузеров плохо/нестабильно поддерживает русский и вообще много языков, а Deepgram Nova-3 Multilingual даёт стабильное качество сразу на десятках языков через одно WS-соединение.
- **Перевод текста, а не голоса** — генерация синтетической речи на лету (voice translation) сильно сложнее, дороже и заметно задерживает разговор. Текстовый перевод — быстрый и достаточно понятный компромисс для учебного контекста.

## История: почему Deepgram, а не AssemblyAI

Первая версия использовала AssemblyAI (`universal-3-5-pro`), но её конфигурация не поддерживала русский язык — соответственно, не работал и перевод для русскоязычных участников. Заменили STT-провайдера на **Deepgram Nova-3 Multilingual**, который:

- поддерживает русский и 35+ языков в потоковом режиме;
- даёт $200 бесплатных кредитов при регистрации без карты;
- тарифицируется только за отправленное аудио.

Подробности замены см. в [`CHANGELOG.md`](./CHANGELOG.md).

**Важный нюанс про авторизацию в браузере.** У Deepgram браузерный `WebSocket` не может выставить заголовок `Authorization`, поэтому официально задокументированный способ — передать API-ключ вторым аргументом конструктора `WebSocket` (используется механизм `Sec-WebSocket-Protocol`):

```js
new WebSocket(`wss://api.deepgram.com/v1/listen?${params}`, ['token', DEEPGRAM_API_KEY]);
```

(Проверьте актуальную документацию Deepgram, если этот код перестанет подключаться — провайдеры API периодически меняют детали авторизации.)

## Быстрый старт

### 1. Получить API-ключ Deepgram

1. Зарегистрироваться на [console.deepgram.com](https://console.deepgram.com/) (карта не нужна, дают $200 бесплатных кредитов).
2. Создать API Key в консоли.
3. Вставить его в `translator.html`, в самом начале блока `<script>`:

```js
const DEEPGRAM_API_KEY = 'ВСТАВЬ_СЮДА_СВОЙ_DEEPGRAM_API_KEY';
```

> ⚠️ Ключ сейчас лежит прямо в клиентском коде — он будет виден любому, кто откроет DevTools. Это нормально для MVP/демо, но **перед публичным продакшеном ключ обязательно нужно перенести на бэкенд** (см. раздел [«Технический долг»](#технический-долг-и-на-что-обратить-внимание)).

### 2. Открыть приложение

Камера и микрофон в браузере работают только в «безопасном контексте»:

- локально: `http://localhost` работает без HTTPS (браузеры делают для localhost исключение);
- при показе кому-то ещё или деплое: обязательно нужен **HTTPS**.

Локально проще всего поднять статичный сервер, например:

```bash
# любой из вариантов
python3 -m http.server 8080
# или
npx serve .
```

и открыть `http://localhost:8080/translator.html`.

### 3. Проверить звонок

1. Открыть `translator.html` в двух вкладках/устройствах.
2. В одной — «📹 Создать комнату», скопировать 4-значный ID.
3. Во второй — «🔑 Войти по ID», ввести скопированный ID.
4. Разрешить доступ к камере/микрофону в обеих вкладках.
5. Начать говорить — нажать «🎤 Начать запись».

## Структура репозитория

```
translator.html   — всё приложение: разметка, стили, логика (единый файл)
README.md         — этот файл
CHANGELOG.md       — история значимых изменений
```

Файл `translator.html` внутри разбит на понятные секции комментариями (`==================== ... ====================`) в теге `<script>`:

- **CONFIG** — API-ключ Deepgram.
- **STATE** — все переменные состояния приложения.
- **DOM** — ссылки на элементы интерфейса.
- **UTILITIES** — вспомогательные функции (тосты, статус-бар, таймер звонка и т.п.).
- **MIC LIST** — получение и выбор микрофона.
- **TRANSLATION DISPLAY** — отрисовка перевода/истории сообщений.
- **INPUT MODE** — переключение голос/текст.
- **MEDIA CONTROLS** — мьют микрофона/камеры, переключение камеры.
- **LOBBY ACTIONS** — создание/вход в комнату.
- **PEER INITIALIZATION** — установление P2P-соединения через PeerJS.
- **DEEPGRAM** — стриминг аудио в Deepgram и обработка транскрипции.
- **TRANSLATION** — вызов MyMemory для перевода текста.
- Остальное — обработчики завершения звонка, смены микрофона, смены языка, ухода со вкладки.

## Куда это движется (дальнейшее развитие)

Текущая версия — это proof of concept для схемы **1 на 1**. Целевой сценарий продукта — **1 ведущий + до 15 участников** в одном занятии, у каждого свой язык, плюс демонстрация экрана ведущим. Это не косметическое расширение, а смена архитектуры в нескольких местах. Ниже — то, что нужно учитывать при дальнейшей разработке.

### 1. Видео/аудио: mesh → SFU

Сейчас PeerJS создаёт **mesh**-топологию: каждый участник напрямую соединяется с каждым. Для 2 человек — 1 соединение, нормально. Для 16 человек (1 ведущий + 15) mesh потребовал бы **120 одновременных P2P-соединений** (и это без учёта того, что у каждого участника был бы свой набор из 15 исходящих видеопотоков) — на практике это не работает: перегружает канал и CPU каждого клиента.

Для группы такого размера нужен **SFU (Selective Forwarding Unit)** — медиасервер, который принимает поток от каждого участника один раз и раздаёт его остальным. Варианты для реализации:

- Готовые SaaS/self-hosted платформы: [LiveKit](https://livekit.io/), [Daily.co](https://www.daily.co/), [Agora](https://www.agora.io/), [100ms](https://www.100ms.live/).
- Self-hosted SFU с открытым кодом: [mediasoup](https://mediasoup.org/), [Janus](https://janus.conf.meetecho.com/), [Ion-SFU](https://github.com/ion-sfu/ion-sfu).

PeerJS в текущем виде для этого не подходит — его стоит заменить целиком на клиент выбранного SFU-решения.

### 2. Перевод для группы: у каждого свой целевой язык

Сейчас перевод жёстко завязан на пару «мой язык / язык собеседника» (`getTargetLang()` просто чередует `ru`↔`en`). В сценарии 1:15 у ведущего один язык, а у каждого из 15 слушателей может быть **свой собственный** целевой язык. Значит:

- STT (Deepgram) ведущего должен запускаться один раз и отдавать общий распознанный текст;
- перевод должен веером расходиться на N языков (по числу уникальных языков в комнате, а не по числу участников — если трое слушателей выбрали немецкий, достаточно перевести на немецкий один раз);
- участники должны говорить о своём выбранном языке заранее (языковой профиль), а сервер/клиент ведущего — держать список активных целевых языков комнаты.

Это уже требует лёгкого бэкенда (или облачной функции), который принимает распознанный текст, переводит на нужный набор языков и рассылает нужным участникам — через тот же дата-канал SFU или отдельный WebSocket/PubSub (например, Redis Pub/Sub, Ably, Pusher, Socket.IO).

### 3. Демонстрация экрана

Нужно добавить кнопку «Показать экран» у ведущего, используя `navigator.mediaDevices.getDisplayMedia()`, и передавать этот поток как отдельную видеодорожку через SFU остальным участникам (обычно показывается как второй, увеличенный видеослот, а видео докладчика уменьшается в угол — стандартный паттерн видеоконференций).

### 4. Роли участников

В mesh-версии все участники симметричны. В версии 1:15 нужно ролевое разделение:

- **Ведущий** — может демонстрировать экран, возможно единственный, чья речь переводится всем;
- **Участник** — смотрит видео/экран ведущего, видит перевод на своём языке, может (или не может) говорить сам.

Это тоже требует бэкенда — минимум простой комнаты с ролями и списком участников (кто есть кто, кто говорит сейчас).

### 5. Прочее, что стоит продумать заранее

- **Идентификатор комнаты**: 4 цифры дают всего 9000 комбинаций и не проверяют, что комната ещё существует — для боевого использования (тем более платного продукта) стоит перейти на более длинные/непредсказуемые ID и завести серверный реестр активных комнат.
- **Лимиты MyMemory**: бесплатный анонимный тариф ограничен **5000 символов в сутки** (лимит считается на IP-адрес; при указании email в запросе — 50 000 символов/сутки). Для живого группового занятия это исчерпывается очень быстро. Перед масштабированием на 1:15 стоит присмотреться к платным движкам перевода (DeepL API, Google Cloud Translation, Azure Translator) или к переводу через LLM (например, Claude/GPT) для лучшего качества и учёта контекста разговора.
- **Субтитры vs отдельный текстовый поток**: при 15 слушателях с разными языками поток переводов может быть «шумным» — стоит подумать над UX (субтитры поверх видео, история сообщений, возможность скрыть/показать).

## Технический долг и на что обратить внимание

Пункты, о которых стоит помнить при развитии проекта дальше — они осознанно допустимы для MVP, но не для продакшена:

- **API-ключ Deepgram лежит в клиентском коде.** Нужно вынести вызов Deepgram (и в будущем — перевода) на маленький бэкенд/прокси, который держит ключ в секрете и, например, выдаёт клиенту одноразовый временный токен (Deepgram поддерживает [temporary tokens](https://developers.deepgram.com/docs/temporary-token-authentication) специально для такого сценария).
- **Нет обработки сетевых сбоев PeerJS "по-взрослому".** Если сигнальный сервер PeerJS Cloud недоступен или собеседник за жёстким NAT/файрволом без доступного TURN-сервера — звонок может не установиться. Для продакшена нужен свой TURN-сервер (например, [coturn](https://github.com/coturn/coturn)) вместо дефолтного STUN-only конфига PeerJS.
- **Перевод «в одну сторону за раз»**: если оба участника говорят одновременно, переводы могут визуально «наезжать» друг на друга — стоит продумать очередь/индикацию, кто сейчас говорит.
- **Нет тестов и мониторинга.** Сейчас нет автоматических проверок работоспособности — стоит хотя бы вручную проверять STT/перевод/видео после любых правок перед мержем.
